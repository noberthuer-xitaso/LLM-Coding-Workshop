Dieses Dokument ergänzt die Geschäftsregeln (`business-rules.adoc`) und die Use-Case-Spezifikationen (`uc-*.adoc`) des Systems *Leihgut* um zwei Querschnittsthemen:

. *Validierungsregeln* — präzise Formeln, Algorithmen und Edge Cases für die wichtigsten berechneten oder geprüften Größen.
. *BR-Traceability-Matrix* — vollständige Zuordnung aller Geschäftsregeln zu Use Cases und Gherkin-Szenarien.

=== Validierungsregeln

==== Kautionsberechnung (BR-04)

===== Algorithmus

[source]
----
raw        = wiederbeschaffungswert_euro * 0.20
gerundet   = kaufmaennisch_runden(raw)          // 0.5 wird aufgerundet
kaution    = max(5, min(100, gerundet))
----

Die Kaution wird in *ganzen Euro* ausgewiesen.
Kaufmännisches Runden bedeutet: Nachkommastellen ≥ 0,5 werden aufgerundet, < 0,5 abgerundet
(Beispiel: 15,5 → 16; 15,4 → 15).

===== Wertetabelle

[cols="^1,^1,^1,^1,^2", options="header"]
|===
|WBW (€) |raw (20 %) |gerundet |angewendete Grenze |Kaution (€)

|10  |2,00  |2   |Minimum (5 €)  |*5*
|24  |4,80  |5   |Minimum (5 €)  |*5*
|25  |5,00  |5   |Minimum (5 €)  |*5*
|26  |5,20  |5   |—              |*5*
|75  |15,00 |15  |—              |*15*
|76  |15,20 |15  |—              |*15*
|77  |15,40 |15  |—              |*15*
|78  |15,60 |16  |—              |*16*
|100 |20,00 |20  |—              |*20*
|249 |49,80 |50  |—              |*50*
|250 |50,00 |50  |—              |*50*
|497 |99,40 |99  |—              |*99*
|498 |99,60 |100 |Maximum (100 €)|*100*
|500 |100,00|100 |Maximum (100 €)|*100*
|600 |120,00|120 |Maximum (100 €)|*100*
|===

===== Edge Cases

* *WBW = 1 €* → raw = 0,20 → gerundet = 0 → Minimum → Kaution = 5 €.
* *WBW = 25 €* → raw = 5,00 → gerundet = 5 → Minimum greift *exakt* (kein Abzug) → Kaution = 5 €.
* *Grenze Minimum/frei* liegt bei WBW ≥ 25 €, sofern raw ≥ 5,0 nach Runden.
* *Grenze frei/Maximum* liegt bei WBW = 497 € (Kaution 99 €) vs. 498 € (Kaution 100 €).
* *WBW ist immer ein positiver Ganzbetrag* (BR-03); Dezimalwerte sind nicht erlaubt.

===== Implementierungshinweis

In Java/Kotlin: `Math.round(raw)` verwendet kaufmännisches Runden (HALF_UP bei .5).
In Python: `round()` verwendet _Banker's Rounding_ (HALF_EVEN); stattdessen
`decimal.Decimal(...).quantize(Decimal('1'), rounding=ROUND_HALF_UP)` verwenden.

==== Rückgabefrist (BR-09)

===== Berechnung bei Ausgabe

[source]
----
rueckgabefrist = ausgabe_datum + kategorie.leihdauer_tage  // Kalendertage
----

* *Ausgabe 2026-09-01*, Leihdauer 14 Tage → Frist *2026-09-15*.
* Das Ausgabedatum selbst zählt als Tag 0; Tag 14 ist der letzte Rückgabetag.
* Wochentage und Feiertage werden nicht berücksichtigt; es gelten reine Kalendertage.

===== Verlängerung (BR-10)

[source]
----
neue_rueckgabefrist = aktuelle_rueckgabefrist + kategorie.leihdauer_tage
----

* Die Verlängerung verlängert die *bestehende Frist*, nicht das heutige Datum.
* Beispiel: Frist 2026-09-15, Leihdauer 14 Tage → neue Frist *2026-09-29*.

===== Überfälligkeitsprüfung (BR-35)

[source]
----
ist_ueberfaellig = (heute > rueckgabefrist) AND (rueckgabe_datum IS NULL)
----

* Frist *gleich* heute: *nicht überfällig*.
* Status `in_Prüfung` (Gegenstand wurde zurückgegeben, Prüfprotokoll noch offen):
  `rueckgabe_datum IS NOT NULL` → *nicht mehr überfällig* für Sperrzwecke.

==== Reservierungsverfall (BR-31)

===== Berechnung

[source]
----
verfall_datum = entstehung_datum + 3 Kalendertage
ist_verfallen  = (aktuelles_datum > verfall_datum)
----

* *Entstehung 2026-09-01* → Verfall_Datum = *2026-09-04*.
* Am 01., 02., 03.09. ist die Reservierung *gültig*; ab 04.09. ist sie *verfallen*
  (das System prüft `aktuelles_datum > verfall_datum`, d. h. erst wenn der vierte Tag
  begonnen hat).
* Das Mitglied hat also *drei volle Abholungstage* nach dem Entstehungstag.

===== Verfall-Auslösung

Das System prüft den Verfall beim nächsten systemrelevanten Ereignis
(z. B. nächste Ausgabe-Anfrage für den Gegenstand, nächste Reservierungsanfrage
derselben Kategorie). Es gibt keinen expliziten Hintergrundprozess als Anforderung.

===== Folgen des Verfalls

[source]
----
wenn ist_verfallen:
  1. Reservierung stornieren
  2. falls nächste Vormerkung in Warteschlange vorhanden:
       neues_verfall_datum = heute + 3 Tage
       Reservierung für nächstes nicht-gesperrtes Mitglied anlegen (BR-33)
  3. sonst:
       gegenstand.zustand = verfügbar
----

==== Ausleihlimit (BR-06)

===== Prüfbedingung

[source]
----
aktive_ausleihen = COUNT(Ausleihe
  WHERE mitglied_id = X
  AND status IN {aktiv, in_Prüfung})

ausgabe_verweigert = (aktive_ausleihen >= 3)
----

* Status `aktiv`: Gegenstand ist ausgegeben, Prüfprotokoll fehlt noch.
* Status `in_Prüfung`: Gegenstand wurde zurückgegeben (UC-03), Prüfprotokoll noch nicht erstellt —
  zählt weiterhin als aktive Ausleihe des Mitglieds.
* Status `abgeschlossen`: zählt *nicht* mit.
* *Vormerkungen zählen nicht mit* (BR-06 ausdrücklich).

===== Grenzwert-Tabelle

[cols="^1,^2", options="header"]
|===
|Aktive Ausleihen |Ausgabe möglich?
|0 |Ja
|1 |Ja
|2 |Ja
|3 |*Nein* (Limit erreicht, `AUSLEIHLIMIT_ERREICHT`)
|===

==== Kautionsabzug (BR-21)

===== Wertebereich

[source]
----
0 ≤ kautionsabzug ≤ ausleihe.kaution_betrag_euro
----

* Negativer Abzug ist *nicht erlaubt* (HTTP 422, `KAUTIONSABZUG_NEGATIV`).
* Abzug > hinterlegte Kaution ist *nicht erlaubt* (HTTP 422, `KAUTIONSABZUG_ZU_HOCH`).
* Abzug = 0 ist erlaubt (keine Beschädigung, volle Rückerstattung).
* Abzug = hinterlegte Kaution ist erlaubt (vollständige Einbehaltung, z. B. bei Verlust).

===== Verloren-Erklärung (BR-19)

[source]
----
wenn nachzustand = verloren:
  kautionsabzug = ausleihe.kaution_betrag_euro   // automatisch 100 %
  gegenstand.zustand = ausgemustert
----

Der vom Wart eingegebene `kautionsabzug`-Wert wird in diesem Fall ignoriert und
systemseitig auf die volle Kaution gesetzt (BR-19 hat Vorrang).

==== Sperre (BR-34 / BR-35 / BR-36)

===== Eintritt der Sperre (BR-34)

[source]
----
ist_gesperrt = EXISTS(
  Ausleihe
  WHERE mitglied_id = X
  AND status = aktiv
  AND rueckgabefrist < heute
)
----

* Ausleihen mit `status = in_Prüfung` sind *nicht* überfällig im Sperrsinne
  (Gegenstand zurückgegeben → `rueckgabe_datum IS NOT NULL`).
* Die Sperre gilt solange, wie *mindestens eine* überfällige Ausleihe existiert.

===== Ende der Sperre (BR-36)

[source]
----
sperre_aufgehoben = NOT EXISTS(
  Ausleihe
  WHERE mitglied_id = X
  AND status = aktiv
  AND rueckgabefrist < heute
)
----

Die Sperre endet *automatisch*, wenn für alle überfälligen Ausleihen des Mitglieds
das Prüfprotokoll abgeschlossen wurde (Status wechselt zu `abgeschlossen`).

===== Wirkungen der Sperre

[cols="3,^1", options="header"]
|===
|Aktion |Gesperrtes Mitglied erlaubt?
|Neue Ausleihe (UC-01)              |*Nein* (BR-07)
|Verlängerung (UC-02)               |*Nein* (implizit über Überfälligkeit)
|Vormerken (UC-05)                  |*Ja* (BR-33)
|Reservierung abholen (UC-01)       |*Nein* (BR-07); Reservierung wird übersprungen (BR-33)
|===

==== Wartungsintervall (BR-23 / BR-24)

===== Nutzungszähler-Aktualisierung

[source]
----
// Bei Abschluss eines Prüfprotokolls (UC-04) oder Verloren-Erklärung (UC-07):
gegenstand.nutzungszaehler += 1
nutzungszaehler_neu = gegenstand.nutzungszaehler

// Vorrangregel BR-24:
wenn nutzungszaehler_neu >= kategorie.wartungsintervall_ausleihen:
  effektiver_nachzustand = wartungsfällig   // überschreibt jede andere Eingabe
sonst:
  effektiver_nachzustand = eingegebener_nachzustand
----

IMPORTANT: *BR-24 hat Vorrang* vor dem explizit gesetzten Nachzustand `verfügbar`.
Auch wenn der Wart `verfügbar` eingibt, erzwingt ein erreichtes Wartungsintervall
den Zustand `wartungsfällig`.

===== Ausnahme: Nachzustand `verloren` / `ausgemustert`

[source]
----
wenn nachzustand_eingabe IN {verloren, ausgemustert}:
  // BR-19 / BR-17 haben Vorrang — Gegenstand wird ausgemustert
  // Nutzungszähler wird trotzdem inkrementiert (BR-23)
  // Wartungsintervall-Prüfung ist irrelevant (Gegenstand wird stillgelegt)
----

===== Wartung abschließen (BR-25)

[source]
----
// Eigenständige Aktion — KEIN Prüfprotokoll, KEINE Ausleihe-ID (UC-06)
gegenstand.nutzungszaehler = 0
gegenstand.zustand = verfügbar  // oder reserviert, falls Vormerkung vorliegt (BR-30)
----

Nach der Wartung beginnt der Zähler bei 0; das Intervall gilt neu.

==== Inventarnummern-Format (BR-01)

* *Eindeutigkeit*: Die Inventarnummer muss systemweit eindeutig sein.
* *Format*: Beliebiger nicht-leerer String, maximal 50 Zeichen.
* *Beispiele*: `WZ-042`, `BH-001`, `GG-0042`.
* Die Inventarnummer wird nie gelöscht — nur der Gegenstand-Zustand wechselt
  (auf `ausgemustert`).
* Bei Dopplung: HTTP 409, Fehlercode `INVENTARNUMMER_DOPPELT`.

---

==== Einweisungspflicht (BR-08)

===== Prüfbedingung

[source]
----
einweisung_vorhanden = EXISTS(
  Einweisung
  WHERE mitglied_id = X
  AND kategorie_id = gegenstand.kategorie_id
)

ausgabe_erlaubt =
  NOT kategorie.einweisungspflichtig
  OR einweisung_vorhanden
----

* Ist die Kategorie *nicht* einweisungspflichtig: keine Prüfung nötig.
* Ist die Kategorie einweisungspflichtig: Einweisung muss für *diese Kategorie*
  (nicht für einzelnen Gegenstand) dokumentiert sein.
* Bei fehlender Einweisung: HTTP 422, Fehlercode `EINWEISUNG_FEHLT`.
