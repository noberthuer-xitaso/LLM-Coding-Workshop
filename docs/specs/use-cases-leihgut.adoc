== Persona Use Cases (Cockburn Fully Dressed)

=== UC-01 Gegenstand ausgeben (Check Out an Item)

*Primary Actor:* Counter staff (Karim)

*Trigger:* A member presents an item for borrowing.

*Stakeholders & Interests:*

* Counter staff — needs an instant yes/no decision.
* Member — wants the item now.
* Organisation — wants the deposit captured correctly and the loan traceable.

*Preconditions:*

* The item exists in the catalogue.
* The item is in state `verfuegbar` or `reserviert` (for this member).
* The member has no more than 2 other active loans.
* The member has no overdue loan.
* If the item's category requires training, the member holds a valid `Einweisung`.

*Main Success Scenario:*

. Counter staff submits checkout request (member ID, item ID, counter staff ID).
. System verifies all preconditions.
. System records the deposit at the current catalogue value (snapshot, not recomputed later).
. System sets the item state to `ausgeliehen`.
. System creates an `Ausleihe` with state `aktiv`.
. System writes two audit log entries in the same transaction.
. System returns the new loan with deposit amount.

*Extensions:*

* 2a. Item is `reserviert` but not for this member → reject with `GegenstandReserviert`.
* 2b. Member already has 3 active loans → reject with `AusleiheLimitErreicht`.
* 2c. Member has an overdue loan → reject with `MitgliedGesperrt`.
* 2d. Category requires training, member has none → reject with `EinweisungFehlt`.
* 2e. Concurrent checkout of the same item by another process → reject with `NebenlaeufigeAusgabeAbgelehnt` (HTTP 409); enforced by `BEGIN IMMEDIATE` + partial unique index.

*Postconditions:*

* An `Ausleihe` record exists with state `aktiv`, deposit snapshot, and timestamps.
* Item state is `ausgeliehen`.
* Two audit entries are written and immutable.

*Business Rules:* BR-AUS-01, BR-AUS-02, BR-AUS-03, BR-AUS-04, BR-AUS-05.

[`src/leihgut/anwendungskern/ausleihe_service.py:144-246`]

=== UC-02 Ausleihe verlängern (Extend a Loan)

*Primary Actor:* Counter staff

*Trigger:* Member requests an extension before the due date.

*Preconditions:*

* Loan exists and is `aktiv`.
* Loan has not been extended before.
* Loan is not overdue.

*Main Success Scenario:*

. Counter staff submits extension request (loan ID, new due date).
. System verifies preconditions.
. System updates the loan's due date and marks the extension flag.
. System writes an audit entry.

*Extensions:*

* 2a. Loan already extended → reject with `BereitsVerlaengert`.
* 2b. Loan is overdue → reject with `AusleiheUeberfaellig`.
* 2c. Open reservation exists for this category — _check currently deferred (see Known Gaps)_.

*Business Rules:* BR-AUS-06, BR-AUS-07.

[`src/leihgut/anwendungskern/verlaengerung_service.py:102`]

=== UC-03 Gegenstand zurücknehmen (Return an Item)

*Primary Actor:* Counter staff

*Trigger:* Member returns a borrowed item at the counter.

*Preconditions:*

* Loan exists and is `aktiv`.

*Main Success Scenario:*

. Counter staff submits return (loan ID).
. System sets loan state to `zurueckgegeben`.
. System sets item state to `in_pruefung`.
. System auto-cancels the first open reservation for the item's category (FIFO).
. System writes two audit entries in the same transaction.
. System notifies counter staff that inspection is pending.

*Postconditions:*

* Loan is `zurueckgegeben`; item is `in_pruefung`.
* First reservation in queue (if any) is `automatisch_abgesagt`.

*Business Rules:* BR-RUP-01, BR-VOR-02.

[`src/leihgut/anwendungskern/ausleihe_service.py:251-314`, `src/leihgut/anwendungskern/vormerkung_service.py:121-147`]

=== UC-04 Prüfung abschließen (Close Inspection)

*Primary Actor:* Workshop manager (Rolf)

*Trigger:* Returned item has been inspected.

*Preconditions:*

* Loan is `zurueckgegeben`.
* Item is `in_pruefung`.
* Requested deposit deduction ≤ deposited amount.

*Main Success Scenario:*

. Rolf submits inspection result (loan ID, damage list, deposit deduction).
. System deduplicates damage entries by exact description per item.
. System increments the item's usage counter.
. System determines next item state: `wartungsfaellig` if counter ≥ interval, else `verfuegbar` (or `reserviert` if queue exists).
. System executes one atomic `BEGIN IMMEDIATE` transaction writing: loan close, item state, inspection report, damage entries, deposit movement(s), audit entry.

*Extensions:*

* 2a. Deduction > deposited amount → reject with `KautionsAbzugZuHoch`.
* 4a. After maintenance threshold reached → item state `wartungsfaellig`.
* 4b. After maintenance threshold reached AND open reservation → item state stays `wartungsfaellig` (maintenance comes first).

*Postconditions:*

* Loan is `abgeschlossen`; item is in new state.
* Deposit movement is recorded (if deduction > 0: `SCHADENSABZUG`; remainder: `RUECKZAHLUNG`).

*Business Rules:* BR-RUP-04, BR-RUP-05, BR-WAR-01, BR-WAR-02, BR-KAU-02.

[`src/leihgut/anwendungskern/pruefung_service.py:100-230`, `src/leihgut/adapters/persistence/sqlite_pruefabschluss_repository.py:21-101`]

=== UC-05r Vormerkung erfassen (Place a Reservation)

*Primary Actor:* Member (Sabine)

*Trigger:* Member requests to be notified when a category of item becomes available.

*Preconditions:*

* Member has no open reservation for the same category.
* Member is not blocked — _check currently a stub; see Known Gaps_.

*Main Success Scenario:*

. Member submits reservation (member ID, category ID).
. System verifies uniqueness constraint.
. System creates `Vormerkung` with state `offen`.
. System returns reservation ID.

*Business Rules:* BR-VOR-01, BR-VOR-02.

[`src/leihgut/anwendungskern/vormerkung_service.py:59`]

=== UC-05m Wartung abschließen (Finish Maintenance)

*Primary Actor:* Workshop manager

*Trigger:* Maintenance work on a `wartungsfaellig` item is complete.

*Preconditions:*

* Item is `wartungsfaellig`.

*Main Success Scenario:*

. Rolf submits maintenance completion (item ID).
. System resets usage counter to 0.
. System sets item state to `reserviert` if an open reservation exists, else `verfuegbar`.
. System writes audit entry.

*Business Rules:* BR-WAR-03, BR-VOR-03.

[`src/leihgut/anwendungskern/wartung_service.py:62`]

=== UC-06 Verlust erfassen (Record a Loss)

*Primary Actor:* Counter staff

*Trigger:* A borrowed item has been reported lost.

*Preconditions:*

* Loan is `aktiv`.

*Main Success Scenario:*

. Counter staff submits loss report (loan ID).
. System executes one atomic `BEGIN IMMEDIATE` transaction:
  .. Sets loan to `abgeschlossen_verloren`.
  .. Sets item to `ausgemustert`.
  .. Inserts `VERLUST_EINZUG` deposit movement (100 % of deposited amount).
  .. Writes two audit entries.

*Business Rules:* BR-VER-02, BR-VER-03, BR-KAU-03/04.

[`src/leihgut/anwendungskern/verlust_service.py:48-175`]

=== UC-09 Katalog verwalten (Manage Catalogue)

*Operations:* Create category, update category, decommission item, create item.

=== Interface Contracts

==== Time

All time reads go through `Clock.jetzt()`, which returns an ISO-8601 string.
[`src/leihgut/ports/clock.py:14-18`]

==== Deposit Calculation

`kaution_berechnen(wiederbeschaffungswert_cent: int) -> int`

* Input: replacement value in cents (integer > 0).
* Processing: `round(value * 0.2 / 100) * 100`.
* Output: always a multiple of 100 cents; bounded to [500, 10 000].
* This is the only place in the codebase where deposit amount is computed.

[`domain/kaution.py:7-20`]

== Known Gaps

* *Extension blocks reservation* — BR-AUS-07 check for `VormerkungOffen` is commented out with `# UNCOMMENT mit EPIC-E` in [`src/leihgut/anwendungskern/verlaengerung_service.py:128-131`].

* *Initial deposit ledger entry* — `HINTERLEGUNG` movement type defined but never written [`src/leihgut/domain/kautionsbewegung.py:14-15`].
