== Q1 What problem does this bounded context solve, and for whom?

=== Q1.1 Product identity
[ANSWERED] Leihgut is a digitised lending-management system for a "Bibliothek der Dinge" (library of things) that loans tools and devices to its members. Today the process uses a ring-binder and cash deposits; the system replaces it. Evidence: `README.adoc:11-24`.

=== Q1.2 Primary users
[ANSWERED] Three personas are named: Karim (counter staff, `thekendienst`) who needs instant authorisation decisions; Sabine (member, `mitglied`) who wants availability and reservations; and Rolf (workshop manager, `wart`) who handles inspections, maintenance, and training. Evidence: `README.adoc:43-49`, `src/leihgut/adapters/rest/rollen.py:13-27`.

=== Q1.3 Channels
[ANSWERED] The system exposes one REST API (FastAPI) and a CLI; there is deliberately no web UI. Evidence: `README.adoc:50-59`, `src/leihgut/adapters/rest/app.py:254-592`.

=== Q1.4 Why built
[ANSWERED] Three concrete failures drive the build: deposits are paid out incorrectly, maintenance-due items are still handed out, and reservations are ignored when a loan is extended. Evidence: `README.adoc:17-24`.

=== Q1.5 Success metrics
[OPEN] Category: business-context. Ask role: Product Owner.

=== Q1.6 Segment priority

== Q3 What is the architecture of this bounded context?

=== Q3.1 Introduction and Goals
[ANSWERED] The system is a learning project that builds a real, deployable lending tool. The repository narrates the goal as: the counter always knows whether an item may be issued, every deposit movement is traceable, maintenance-due items are withheld, and reservations are honoured. Evidence: `README.adoc:6-24`, `README.adoc:61-80`.

=== Q3.2 Constraints
[ANSWERED] Explicit constraints from the README:
- Single locally startable process, no external services.
- REST API plus CLI; no web UI.
- No real authentication; role is read from an `X-Rolle` header, not verified.
- Date/time must come from a replaceable source so deadlines are testable.

Evidence: `README.adoc:50-59`, `src/leihgut/ports/clock.py:1-18`, `src/leihgut/adapters/rest/rollen.py:1-27`.

=== Q3.3 Context and Scope
[ANSWERED] The entire bounded context lives in the `leihgut` Python package. No other package depends on it, and it calls no external service. Membership data (member existence and identity) is treated as an opaque `mitglied_id` string; there is no member management use case and no FK to a members table. Evidence: `src/leihgut/adapters/persistence/schema.sql:61-65`, `src/leihgut/domain/ausleihe.py:25`.

=== Q3.4 Solution Strategy
[ANSWERED] Hexagonal architecture (Ports & Adapters):
- Domain layer: pure frozen dataclasses and pure functions, zero imports from the framework.
- Port layer: Python `Protocol` (or `ABC`) interfaces per aggregate.
- Application kernel: use-case functions that receive ports via dependency injection; split by IOSP — one pure validation function and one integration function per use case.
- Adapter layer: SQLite repositories, FastAPI router, `SystemClock`.

Evidence: `src/leihgut/ports/ausleihe_repository.py:1-44`, `src/leihgut/anwendungskern/ausleihe_service.py:105-139`, `src/leihgut/adapters/persistence/sqlite_ausleihe_repository.py:1-93`, `src/leihgut/adapters/rest/app.py:1-12`.

=== Q3.5 Building Block View
[ANSWERED] Layers and their representative files:

[cols="1,2,2"]
|===
| Layer | Description | Representative file
| Domain | Aggregates, value objects, state enums | `domain/ausleihe.py:14-41`
| Ports | `Protocol`/`ABC` interfaces, one per aggregate | `ports/ausleihe_repository.py:17-43`
| Application kernel | Use-case functions, typed rejection return values | `anwendungskern/ausleihe_service.py:144-315`

| Clock adapter | `SystemClock` wraps `datetime.now(UTC)` | `adapters/system_clock.py:1-13`
|===

=== Q3.6 Runtime View
[ANSWERED] The critical runtime flows:

==== Q3.6.1 Checkout (UC-01)
Read item → read category → read open loans (for limit/overdue check) → read training → conditionally read reservation queue → validate (pure `_ausgabe_pruefen`) → `BEGIN IMMEDIATE` → insert loan → update item state → write two audit entries → commit.
Evidence: `src/leihgut/anwendungskern/ausleihe_service.py:144-246`.

==== Q3.6.2 Return (UC-03)
Validate loan is active → update loan to `zurueckgegeben` → update item to `in_pruefung` → call `vormerkungs_verwalten_nach_rueckgabe` (auto-cancel first reservation) → write two audit entries.
Evidence: `src/leihgut/anwendungskern/ausleihe_service.py:251-314`, `src/leihgut/anwendungskern/vormerkung_service.py:121-147`.

==== Q3.6.3 Inspection close (UC-04)
Validate loan in `zurueckgegeben` and item in `in_pruefung` → validate deduction ≤ deposit → compute damage dedup → increment counter → determine next state → `BEGIN IMMEDIATE` → atomically write loan, item, inspection report, damage entries, deposit movements, audit entry.
Evidence: `src/leihgut/anwendungskern/pruefung_service.py:100-230`, `src/leihgut/adapters/persistence/sqlite_pruefabschluss_repository.py:21-101`.

==== Q3.6.4 Loss (UC-06)
Validate loan active → `BEGIN IMMEDIATE` → set loan to `abgeschlossen_verloren` → set item to `ausgemustert` → insert `VERLUST_EINZUG` deposit movement → write two audit entries → commit.
Evidence: `src/leihgut/anwendungskern/verlust_service.py:48-175`.

=== Q3.7 Deployment View
[ANSWERED] The system is a single process. SQLite is a local file opened with `check_same_thread=False`; FastAPI runs under uvicorn. Tests use `:memory:` databases. There is no container definition or cloud configuration in the repository. Evidence: `src/leihgut/adapters/persistence/sqlite_gegenstand_repository.py:10-25`, `pyproject.toml:6-11`.

=== Q3.8 Crosscutting Concepts

==== Q3.8.1 Security — threat model T-004
[ANSWERED] Roles are passed in `X-Rolle` header and are not cryptographically verified. The README and code comment this explicitly as a known, intentional limitation. Evidence: `README.adoc:57-58`, `src/leihgut/adapters/rest/rollen.py:1-27`.

==== Q3.8.2 Audit trail — append-only
[ANSWERED] Every state change writes an `AuditLogEintrag` in the same transaction as the domain change. Two database triggers prevent `UPDATE` and `DELETE` on `audit_log`. Evidence: `src/leihgut/adapters/persistence/schema.sql:96-106`, `src/leihgut/adapters/persistence/sqlite_audit_log_repository.py:17-37`.

==== Q3.8.3 Test concept
[ANSWERED] Hamburg-Style TDD: pure `_operation` functions are unit-tested without ports; integration functions are tested against `:memory:` SQLite (no mocking of repositories). Every test references its UC-ID or BR-ID in a comment. Evidence: `src/leihgut/anwendungskern/ausleihe_service.py:105-107`, `tests/test_epic_a_ausleihe.py:134-229`, `README.adoc:63-68`.

==== Q3.8.4 Error handling
[ANSWERED] Services return typed rejection dataclasses instead of raising exceptions. The REST adapter maps each type to an HTTP status code via lookup tables. No retry or circuit-breaker is present (single-process in-memory SQLite; no remote calls). Evidence: `src/leihgut/anwendungskern/ausleihe_service.py:34-83`, `src/leihgut/adapters/rest/app.py:127-230`.

==== Q3.8.5 Observability
[ANSWERED] Observability is limited to the append-only audit log and a stats/cleanup admin endpoint. No structured logging, metrics, or distributed tracing are present. Evidence: `src/leihgut/adapters/rest/app.py:540-585`, `src/leihgut/anwendungskern/audit_retention_service.py:141-197`.

=== Q3.9 Architectural Decisions
[ANSWERED] Four ADRs are named in code comments:

- ADR-004: single SQLite file. Evidence: `src/leihgut/adapters/persistence/sqlite_gegenstand_repository.py:1-25`.
- ADR-006: injected `Clock` port for testable deadlines. Evidence: `src/leihgut/ports/clock.py:1-18`.
- ADR-007: `BEGIN IMMEDIATE` write lock plus partial unique index on `ausleihe(gegenstand_id) WHERE zustand='aktiv'` to prevent TOCTOU checkout races. Evidence: `src/leihgut/ports/ausleihe_repository.py:7-15`, `src/leihgut/adapters/persistence/schema.sql:55-59`, `src/leihgut/adapters/persistence/sqlite_ausleihe_repository.py:34-60`.
- ADR-009: immutable audit log enforced by DB triggers. Evidence: `src/leihgut/adapters/persistence/schema.sql:93-106`.

=== Q3.10 Quality Requirements
[ANSWERED] Measurable quality behaviours derived from the code:

- Checkout race protection: `BEGIN IMMEDIATE` + partial unique index; a concurrent checkout raises `NebenlaeufigeAusgabeAbgelehnt` and returns `409`. Evidence: `src/leihgut/adapters/persistence/sqlite_ausleihe_repository.py:34-60`.
- Deposit snapshot: `kaution_cent` is frozen at checkout so category-value changes do not alter active loans. Evidence: `src/leihgut/domain/ausleihe.py:28`, `src/leihgut/anwendungskern/ausleihe_service.py:194`.

- Audit immutability: `UPDATE`/`DELETE` on `audit_log` aborts with SQLite error. Evidence: `src/leihgut/adapters/persistence/schema.sql:96-106`, `tests/test_skeleton_01_verfuegbarkeit.py:97-121`.
- Retention policy: hot window = 90 days; warm archival is optional; cold deletion not yet implemented. Evidence: `src/leihgut/anwendungskern/audit_retention_service.py:25-32`.

=== Q5.2 Security risks
[ANSWERED] The `X-Rolle` header is trusted without verification. Any HTTP client that sets the header bypasses all role checks. This is explicitly acknowledged in code and README. Evidence: `src/leihgut/adapters/rest/rollen.py:1-27`, `README.adoc:57-58`.

=== Q5.3 Operational risks
[ANSWERED] The system runs as a single process with one SQLite file. There is no backup strategy, no health endpoint, no graceful shutdown, and no restart procedure documented in the repository. Concurrent writers are serialised with `BEGIN IMMEDIATE`, which serialises all write throughput through SQLite. Evidence: `src/leihgut/adapters/persistence/sqlite_gegenstand_repository.py:10-25`, `src/leihgut/adapters/persistence/sqlite_ausleihe_repository.py:34-60`.

=== Q5.4 Dependency / supply-chain risks
[ANSWERED] `pyproject.toml` specifies only minimum version bounds (`>=`), and there is no `uv.lock` or `pip-compile`-generated lock file in the repository. Builds are not reproducible without an external lock. Evidence: `pyproject.toml:6-19`.

=== Q5.5 Scaling / performance risks
[ANSWERED] The architecture imposes a single-writer ceiling: `BEGIN IMMEDIATE` serialises all writes through SQLite's single-writer model. This is safe for the stated deployment profile (≈ 800 members, open twice a week) but will not scale to concurrent API load without changing the persistence layer. Evidence: `src/leihgut/adapters/persistence/sqlite_ausleihe_repository.py:34-60`, `src/leihgut/adapters/persistence/schema.sql:55-59`.
