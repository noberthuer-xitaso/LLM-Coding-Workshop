== 5. Bausteinsicht

Die Bausteinsicht beschreibt die statische Zerlegung des Systems _Leihgut_ in Bausteine (Module, Komponenten, Schichten) sowie deren Abhängigkeiten.
Das System folgt einer *Layered Architecture* mit vier Schichten und strikter Abhängigkeitsrichtung nach innen (Dependency Inversion Principle).
An Schichtgrenzen werden ausschließlich DTOs und explizite Port-Interfaces übergeben — keine Domänen-Entities werden nach außen exponiert.

==== Enthaltene Bausteine

[cols="2,1,4", options="header"]
|===
|Baustein |Typ |Verantwortung

|REST API
|Container
|Verarbeitet alle neun Anwendungsfälle (UC-01–UC-09) über HTTP/JSON.
Nimmt Requests entgegen, delegiert an die Anwendungsschicht und gibt DTOs zurück.
Keine Geschäftslogik — nur Protokolladaption und Fehlerübersetzung.

|CLI
|Container
|Kommandozeilenschnittstelle für die Wart-Aufgaben UC-04, UC-06, UC-07 und UC-09.
Teilt die Anwendungsschicht vollständig mit der REST API.
Kein doppelter Anwendungscode.

|Datenbank
|Container
|Einzige Persistenzschicht für alle Domänendaten.
In Release 1 SQLite (lokal startbar, keine externe Dienste).
PostgreSQL ist als Ersatz möglich ohne Änderung an der Domänenschicht.
|===

==== Wichtige Schnittstellen nach außen

[cols="2,4", options="header"]
|===
|Schnittstelle |Beschreibung

|`POST /ausleihen`
|Ausgabe eines Gegenstands (UC-01): prüft alle Ausgabebedingungen (Zustand, Sperre, Einweisung, Ausleihlimit, Kaution), legt Ausleihe an.

|`POST /ausleihen/{id}/pruefprotokoll`
|Prüfprotokoll durch Wart (UC-04): schließt Ausleihe ab, löst Zustandsübergang am Gegenstand aus, verbucht Kautionsbewegungen.

|`POST /vormerkungen`
|Vormerkung anlegen (UC-05): prüft Limits, reiht in Warteschlange ein, erzeugt ggf. sofortige Reservierung.

|`POST /gegenstaende/{nr}/wartung-abschliessen`
|Wartung abschließen (UC-06): setzt Zustand auf verfügbar, Nutzungszähler auf null, löst Reservierung aus wenn Vormerker vorhanden.

|CLI `pruefprotokoll`
|Identische fachliche Operation wie REST-Pendant, Eingabe über Parameter/interaktiven Prompt.

|CLI `wartung-abschliessen`
|Identische fachliche Operation wie REST-Pendant.
|===

==== Enthaltene Komponenten

===== API-Schicht

Die Handler-Komponenten übersetzen HTTP-Requests in Service-Aufrufe und Service-Ergebnisse in HTTP-Responses.
Sie enthalten keine Geschäftslogik (IOSP: Kompositions-Funktionen, keine Operationen).

[cols="2,1,4", options="header"]
|===
|Komponente |Use Cases |Verantwortung

|`AusleiheHandler`
|UC-01, UC-02, UC-03
|Nimmt Ausgabe-, Verlängerungs- und Rückgabe-Requests entgegen.
Setzt `X-Role`-Header in Kontext.
Übersetzt Domänenfehler in HTTP 4xx.

|`PruefprotokollHandler`
|UC-04, UC-07
|Prüfprotokoll anlegen (Wart) und Verloren melden.
Nur Rolle `wart`.

|`VormerkungHandler`
|UC-05
|Vormerkung anlegen, stornieren, auflisten.

|`WartungHandler`
|UC-06
|Wartung abschließen.
Nur Rolle `wart`.

|`KatalogHandler`
|UC-08
|CRUD für Kategorien und Gegenstände.
Zustandsändernde Operationen nur für Rolle `wart`.

|`EinweisungHandler`
|UC-09
|Einweisung dokumentieren und widerrufen.
Nur Rolle `wart`.

|`MitgliedHandler`
|—
|Mitglied abrufen inkl. berechnetem Sperr-Prädikat.

|`AuditHandler`
|—
|Audit-Log abrufen und filtern (read-only).
|===

===== Anwendungsschicht (UC-Services)

Jeder Service kapselt genau einen Anwendungsfall.
Services sind reine Kompositionen: Sie orchestrieren Repositories, Domain Services und DateProvider — sie selbst enthalten keine primitiven Berechnungen (IOSP).

[cols="2,4", options="header"]
|===
|Service |Fachliche Verantwortung (Schlüsselregeln)

|`AusleiheService`
|Prüft in definierter Reihenfolge: Gegenstandzustand (BR-05), Ausleihlimit (BR-06), Sperre (BR-07), Einweisung (BR-08).
Bei Bestehen: legt Ausleihe an, hinterlegt Kaution (BR-09), setzt Rückgabefrist, schreibt Audit.

|`VerlaengerungService`
|Prüft: nicht bereits verlängert (BR-10), keine Vormerkung in Kategorie (BR-11), nicht überfällig (BR-11).
Verlängert Frist um volle Leihdauer. Schreibt Audit.

|`RueckgabeService`
|Versetzt Gegenstand von `ausgeliehen` → `in_Prüfung` (BR-12).
Erfasst Auffälligkeiten als Freitext (BR-13).
Beendet die Ausleihe nicht.

|`PruefprotokollService`
|Transaktionaler Kernprozess: legt Prüfprotokoll an (BR-14–18), schließt Ausleihe ab, verbucht Kautionsabzug und Freigabe (BR-20–21), erhöht Nutzungszähler (BR-23), setzt Gegenstandzustand (BR-17, BR-24), löst Reservierung aus wenn Vormerker vorhanden (BR-30).

|`VormerkungService`
|Prüft: max. eine Vormerkung je Mitglied/Kategorie (BR-28).
Reiht in FIFO-Warteschlange ein (BR-29).
Erstellt ggf. sofortige Reservierung wenn Gegenstand verfügbar (BR-30).

|`WartungService`
|Setzt wartungsfälligen Gegenstand auf `verfügbar`, Nutzungszähler auf 0 (BR-25–26).
Erstellt Reservierung wenn Vormerker vorhanden (BR-30).

|`VerlorenService`
|Legt Prüfprotokoll mit `nachzustand = verloren` an (BR-19).
Behält Kaution vollständig ein. Versetzt Gegenstand in `ausgemustert`.

|`KatalogService`
|CRUD für `Kategorie` und `Gegenstand` (BR-01–04).
Berechnet und validiert Kautionsbetrag bei Anlage (BR-04).
Verhindert Kategorienwechsel bei aktiven Ausleihen.

|`EinweisungService`
|Legt Einweisungsdokument an / entzieht es (BR-08).
Einweisung hängt an Mitglied + Kategorie.

|`SystemEventService`
|Bewertet Reservierungsverfall lazy (beim nächsten relevanten Ereignis, BR-31).
Berechnet Sperr-Prädikat als computed view (BR-34–36): kein persistiertes Boolean.
|===

===== Infrastrukturschicht

[cols="2,4", options="header"]
|===
|Komponente |Verantwortung

|`GegenstandRepository`
|Implementiert Port `IGegenstandRepository`.
Persistiert `Gegenstand` und `Kategorie`.
Liefert Gegenstand mit aktuellem Zustand und Nutzungszähler.

|`AusleiheRepository`
|Implementiert Port `IAusleiheRepository`.
Persistiert `Ausleihe`, `Pruefprotokoll`, `Kautionsbewegung`, `Einweisung`.

|`VormerkungRepository`
|Implementiert Port `IVormerkungRepository`.
Persistiert `Vormerkung` und `Reservierung`.
Liefert FIFO-geordnete Warteschlange je Kategorie.

|`AuditRepository`
|Implementiert Port `IAuditRepository`.
Schreibt und liest unveränderliche Audit-Log-Einträge.

|`SystemDateProvider`
|Implementiert Port `IDateProvider`.
Liefert `LocalDate.now()` im Produktivbetrieb.

|`TestDateProvider`
|Implementiert Port `IDateProvider`.
Ermöglicht Fristtests durch injiziertes festes Datum.
Nur für Test-Scope.
|===

==== Aggregate, Entities und Value Objects

[cols="2,1,4", options="header"]
|===
|Klasse |Typ |Verantwortung / Invarianten

|`Kategorie`
|Aggregate Root
|Gruppe gleichartiger Gegenstände. Bestimmt Leihdauer, Wartungsintervall, Einweisungspflicht (BR-02).

|`Gegenstand`
|Entity
|Einzelnes physisches Exemplar mit eindeutiger Inventarnummer (BR-01).
Hält Zustand und Nutzungszähler.
Kennt eigene Ausgabe- und Reservierbarkeitsregeln.

|`Mitglied`
|Aggregate Root
|Person, die ausleihen darf.
Sperre ist kein persistiertes Feld sondern ein vom `SperrPrüfer` berechnetes Prädikat (BR-34–36).

|`Einweisung`
|Entity
|Dokumentierte Unterweisung einer Person für eine Kategorie (BR-08).
Hängt an Mitglied und Kategorie.

|`Ausleihe`
|Aggregate Root
|Vorgang von Ausgabe bis Prüfungsabschluss.
Enthält `Kaution` und `Rückgabefrist` als unveränderliche Value Objects.

|`Kaution`
|Value Object
|Hinterlegter Betrag, berechnet nach `max(5, min(100, round(WBW × 0,20)))` (BR-04).
Nach Hinterlegung unveränderlich.

|`Rückgabefrist`
|Value Object
|Fälligkeitsdatum = Ausgabedatum + Leihdauer (BR-09).
Kennt Methode `überfällig(heute)`.

|`Prüfprotokoll`
|Entity
|Abschlussdokument einer Prüfung (BR-14–18).
Enthält explizit gesetzten `nachzustand` und Kautionsabzug.

|`Kautionsbewegung`
|Entity
|Unveränderlicher Buchungssatz (hinterlegung / abzug / freigabe).
Bildet den vollständigen Audit-Trail der Kaution (BR-22).
Saldo aller Bewegungen einer abgeschlossenen Ausleihe = 0 (INV-18).

|`Vormerkung`
|Aggregate Root
|Platz in der Warteschlange einer Kategorie (BR-27–29).
Max. eine aktive Vormerkung je Mitglied/Kategorie (BR-28).

|`Reservierung`
|Entity
|Einem Mitglied für drei Tage zugeordneter Gegenstand (BR-31).
Verfall und Überspringen bei gesperrtem Mitglied (BR-33).
|===

==== Domain Services

[cols="2,4", options="header"]
|===
|Domain Service |Verantwortung

|`KautionsKalkulator`
|Berechnet den Kautionsbetrag aus dem Wiederbeschaffungswert (BR-04).
Reine Funktion ohne Seiteneffekte.
Folgt IOSP: ausschließlich Operation (primitive Berechnung), keine Komposition.

Die Ports sind Interfaces in der Domänenschicht.

|`IVormerkungRepository`

|Liefert das aktuelle Datum. Austauschbar für Frist-Tests (`TestDateProvider`).

Abhängigkeitsrichtung::
Alle Pfeile zeigen von außen nach innen.
Die Domänenschicht hat keine Abhängigkeit zur Infrastruktur- oder Anwendungsschicht.

IOSP-Prinzip::
Jede Funktion ist entweder *Komposition* (orchestriert andere Funktionen, kein primitiver Code) oder *Operation* (führt primitive Logik aus, keine Aufrufe von anderen Funktionen im System).
Die UC-Services sind reine Kompositionen; `KautionsKalkulator` und `SperrPrüfer` sind reine Operationen.

Anti-Corruption Layer::
Der `MitgliedHandler` (GET /mitglieder) fungiert als Anti-Corruption Layer gegenüber einem zukünftigen externen Mitgliederverwaltungssystem.
In Release 1 werden Mitglieder als einfache Datensätze verwaltet.
Die Schnittstelle bleibt stabil, wenn Mitglieder später über ein externes System importiert werden.
