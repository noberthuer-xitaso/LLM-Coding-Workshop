== Einleitung

Dieses Dokument beschreibt Systemverhalten, das nicht durch einen menschlichen Akteur
ausgelöst wird.
Im Gegensatz zu Use Cases, die auf eine bewusste Benutzeraktion folgen, entstehen diese
Ereignisse durch Zeitablauf oder durch Auswertung persistenter Zustände zum Zeitpunkt
eines Zugriffs.

Das System Leihgut kennt zwei solcher Mechanismen:

SE-01 Reservierungsverfall:: Eine Reservierung, die drei Kalendertage ungenutzt bleibt,
verfällt automatisch.
Das System erkennt diesen Zustand und verarbeitet die Folgen beim nächsten
Zugriff auf den betroffenen Gegenstand oder die betroffene Reservierung
(Lazy Evaluation).

SE-02 Sperre-Berechnung:: Der Sperrstatus eines Mitglieds ist kein gespeichertes Feld,
sondern eine jederzeit aus den aktiven Ausleihen ableitbare Eigenschaft
(Computed Property).
Das System berechnet ihn bei jedem relevanten Zugriff neu.

Beide Mechanismen sind bewusst ohne Hintergrundprozesse oder Scheduler realisiert.
Das entspricht der Rahmenbedingung: _„Ein Prozess, lokal startbar, ohne externe Dienste."_

== SE-01: Reservierungsverfall

=== Beschreibung

Eine Reservierung wird angelegt, wenn ein Gegenstand nach der Prüfung für das erste
Mitglied einer Warteschlange zugeteilt wird (BR-30).
Sie ist drei Kalendertage gültig.
Holt das Mitglied den Gegenstand in dieser Zeit nicht ab, verfällt die Reservierung
(BR-31).

Das System prüft nicht aktiv per Scheduler, ob Reservierungen verfallen sind.
Stattdessen erfolgt die Prüfung unmittelbar vor jeder Operation, die den Zustand
eines Gegenstands oder einer Reservierung berührt.

=== Design-Entscheidung: Lazy Evaluation

[cols="1,3"]
|===
|Entscheidung |Lazy Evaluation — kein Hintergrundprozess, kein Scheduler

|Begründung
|Die Rahmenbedingung schreibt vor: „Ein Prozess, lokal startbar, ohne externe Dienste."
Ein Scheduler ist ein externer Dienst oder erfordert zumindest einen dauerhaft
laufenden Prozess.
Die Öffnungszeiten des Vereins (dienstags und samstags) machen eine zeitgenaue
Prüfung ohnehin irrelevant: Zwischen zwei Öffnungstagen findet keine Ausgabe statt.
Lazy Evaluation ist korrekt und ausreichend.

|Konsequenz
|Ein Verfall wird erst sichtbar, wenn das System das nächste Mal abgefragt wird.
Zwischen zwei Öffnungstagen „passiert" formal nichts — der Zustand wird erst beim
nächsten Zugriff angepasst.
Das ist für dieses System akzeptabel.

|Atomarität
|Der Verfall-Check und die auslösende Operation laufen in derselben Transaktion.
Es gibt keinen Zustand, in dem Reservierungen verfallen sind, aber die Folgewirkungen
(neue Reservierung, Gegenstand verfügbar) noch nicht eingetreten sind.
|===

=== Ablaufbeschreibung

Vor jeder Operation, die den Zustand eines Gegenstands oder einer Reservierung berührt,
führt das System den folgenden Ablauf aus:

. Suche alle Reservierungen mit `verfall_datum < heute`.
. Falls keine gefunden: weiter mit der ursprünglichen Operation.
. Verarbeite jede verfallene Reservierung in Entstehungsreihenfolge (FIFO):
.. Setze Reservierungsstatus auf `verfallen`.
.. Prüfe die Warteschlange der Kategorie auf die nächste aktive Vormerkung.
.. Falls kein weiterer Eintrag in der Warteschlange vorhanden ist:
*** Setze Gegenstandszustand auf `verfügbar`.
.. Falls ein weiterer Eintrag vorhanden ist:
*** Prüfe, ob das Mitglied gesperrt ist (→ SE-02).
*** Falls gesperrt (BR-33): Überspringe dieses Mitglied. Es behält seinen Platz in der
Warteschlange. Prüfe den nächsten Eintrag.
*** Falls nicht gesperrt: Lege neue Reservierung an (BR-30).
Setze `verfall_datum = heute + 3 Kalendertage`.
Stoppe die Verarbeitung der Warteschlange für diesen Gegenstand.
. Führe die ursprüngliche Operation aus.

[plantuml, se01-ablauf, svg]
....
@startuml
skinparam defaultFontName sans-serif
skinparam ActivityBackgroundColor #f5f5f5
skinparam ActivityBorderColor #888888
skinparam ArrowColor #444444

start
:Systemoperation wird aufgerufen\n(GET, POST, DELETE auf Gegenstand\noder Reservierung);

:Suche Reservierungen mit\nverfall_datum < heute;

if (Verfallene Reservierungen\ngefunden?) then (ja)
  while (Nächste verfallene\nReservierung vorhanden?) is (ja)
    :Setze Reservierung\nauf Status "verfallen";
    :Prüfe Warteschlange\nder Kategorie;
    if (Weitere Vormerkung\nin Warteschlange?) then (ja)
      if (Nächstes Mitglied\ngesperrt? (SE-02)) then (ja, BR-33)
        :Überspringe Mitglied;\nPlatz bleibt erhalten;
        :Prüfe nächste\nVormerkung;
      else (nein)
        :Lege neue Reservierung\nfür dieses Mitglied an (BR-30);\nverfall_datum = heute + 3 Tage;
        break
      endif
    else (nein)
      :Setze Gegenstand\nauf "verfügbar";
      break
    endif
  endwhile
else (nein)
endif

:Führe ursprüngliche\nOperation aus;
stop
@enduml
....

=== EARS-Anforderungen

[cols="1,1,4"]
|===
|ID |Typ |Anforderung

|SE-01-REQ-01
|Event-driven
|Wenn das System eine Operation empfängt, die den Zustand eines Gegenstands oder einer
Reservierung berührt, *soll* das System vor Ausführung der Operation alle Reservierungen
mit `verfall_datum < heute` als `verfallen` markieren und die Folgewirkungen (neue
Reservierung oder Gegenstand verfügbar) in derselben Transaktion anwenden.

|SE-01-REQ-02
|State-driven
|Solange die Warteschlange einer Kategorie mindestens eine nicht gesperrte Vormerkung
enthält, *soll* das System bei Verfall einer Reservierung eine neue Reservierung für das
erste nicht gesperrte Mitglied der Warteschlange anlegen und das Verfallsdatum auf
`heute + 3 Kalendertage` setzen.

|SE-01-REQ-03
|Unwanted behaviour
|Wenn beim Verfall-Check das nächste Mitglied in der Warteschlange gesperrt ist,
*soll* das System für dieses Mitglied keine Reservierung anlegen, seinen Platz in der
Warteschlange beibehalten und das nächste Mitglied in der Warteschlange prüfen (BR-33).

|SE-01-REQ-04
|Ubiquitous
|Das System *soll* den Verfall-Check und alle daraus resultierenden Zustandsübergänge
atomar ausführen, sodass kein Zwischenzustand dauerhaft persistiert wird.

|SE-01-REQ-05
|Event-driven
|Wenn nach dem Verfall einer Reservierung keine weitere aktive Vormerkung für die
betreffende Kategorie existiert, *soll* das System den Gegenstandszustand auf
`verfügbar` setzen.
|===

== SE-02: Sperre-Berechnung

=== Beschreibung

Ein Mitglied ist gesperrt, sobald mindestens eine seiner Ausleihen überfällig ist
(BR-34).
Überfällig bedeutet: Die Ausleihe hat den Status `aktiv` und die `rueckgabefrist` liegt
vor dem heutigen Datum (BR-35).
Die Sperre endet automatisch, sobald für alle überfälligen Ausleihen das Prüfprotokoll
abgeschlossen wurde (BR-36).

Es gibt keinen eigenständigen „Entsperr"-Endpunkt.
Der Sperrstatus wird nicht gespeichert, sondern bei jedem relevanten Zugriff neu
berechnet.

=== Design-Entscheidung: Computed Property

[cols="1,3"]
|===
|Entscheidung |Computed Property — kein gespeichertes Feld, keine asynchrone Berechnung

|Begründung
|„Gesperrt" ist zu jedem Zeitpunkt vollständig aus den Ausleihdaten ableitbar.
Ein gespeichertes Flag könnte nach einer Datenmigration, einem manuellen Datenbankeingriff
oder einem Fehler in der Synchronisierungslogik inkonsistent werden.
Die berechnete Variante ist immer korrekt und erfordert keinen Hintergrundprozess.

|Konsequenz
|Jede Operation, die den Sperrstatus eines Mitglieds benötigt, führt eine Datenbankabfrage
durch.
Bei der erwarteten Datenmenge (≤ 800 Mitglieder, ≤ 400 Gegenstände) ist das performant
genug; das Qualitätsziel von 300 ms gilt für die Gesamtantwort.

|Testbarkeit
|Das Datum wird über einen austauschbaren Datums-Provider bereitgestellt
(vgl. PRD, Abschnitt Rahmenbedingungen: „Das System liest das aktuelle Datum über eine
austauschbare Quelle, damit Fristen testbar bleiben.").
Tests können den Provider mit einem beliebigen Datum instrumentieren, ohne Systemzeit
zu manipulieren.
|===

=== Formel

----
gesperrt(mitglied_id) =
  EXISTS (
    SELECT 1
    FROM   Ausleihe
    WHERE  mitglied_id  = :mitglied_id
    AND    status       = 'aktiv'
    AND    rueckgabefrist < today()
  )
----

`today()` ist der über den austauschbaren Datums-Provider gelieferte Wert.
Die Formel wird nicht gecacht und nicht asynchron aktualisiert.

|1
|`POST /ausleihen` — Ausgabe: Gesperrtes Mitglied darf nicht ausleihen (BR-07)
|ja

|2

|ja

|3

|4

|ja

|ja
|===

=== EARS-Anforderungen

[cols="1,1,4"]
|===
|ID |Typ |Anforderung

|SE-02-REQ-01
|State-driven
|Solange ein Mitglied mindestens eine aktive Ausleihe mit `rueckgabefrist < heute` hat,
*soll* das System das Mitglied bei jeder Sperre-Auswertung als gesperrt behandeln.

|SE-02-REQ-02
|Event-driven
|Wenn das Prüfprotokoll der letzten überfälligen Ausleihe eines Mitglieds abgeschlossen
wird, *soll* das System das Mitglied beim nächsten Zugriff als nicht gesperrt ausweisen,
ohne dass ein separater „Entsperr"-Aufruf erforderlich ist.

|SE-02-REQ-03
|Ubiquitous
|Das System *soll* den Sperrstatus eines Mitglieds niemals als persistentes Feld
speichern, sondern ausschließlich durch Auswertung der Formel
`EXISTS(SELECT 1 FROM Ausleihe WHERE mitglied_id = :id AND status = 'aktiv' AND
rueckgabefrist < today())` bestimmen.

|SE-02-REQ-04
|Ubiquitous
|Das System *soll* den Wert von `today()` ausschließlich über einen austauschbaren
Datums-Provider beziehen, sodass der Sperrstatus in Tests ohne Manipulation der
Systemzeit geprüft werden kann.

|SE-02-REQ-05
|Event-driven
|Wenn eine Operation das Mitglied vormerkt (`POST /vormerkungen`) und die Sperre-Formel
`true` liefert, *soll* das System die Vormerkung trotzdem anlegen und lediglich einen
Hinweis zurückgeben, dass das Mitglied derzeit gesperrt ist (BR-33).
|===

=== Verwandte Designentscheidungen

Beide Systemereignisse hängen unmittelbar mit der Rahmenbedingung zusammen, die
Hintergrundprozesse ausschließt.
Sollte diese Einschränkung in einer späteren Release fallen, sind beide Mechanismen
durch Scheduler ersetzbar, ohne dass sich die Geschäftsregeln ändern.

Die Austauschbarkeit des Datums-Providers (SE-02-REQ-04) und die Atomarität des
Verfall-Checks (SE-01-REQ-04) sind architektonisch relevant und sollten in einem
zugehörigen ADR dokumentiert werden.
